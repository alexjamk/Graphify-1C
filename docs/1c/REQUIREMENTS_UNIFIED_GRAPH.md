# Дополнение к требованиям: единый граф основной конфигурации, расширений и визуализация

Нужно дополнить архитектуру Graphify-1C следующими обязательными требованиями.

## 1. Стандартная структура проекта 1С

Основной ожидаемый вариант структуры репозитория:

```text
src/
├── cf/
│   └── выгрузка основной конфигурации
│
└── cfe/
    ├── ExtensionA/
    │   └── выгрузка расширения
    │
    ├── ExtensionB/
    │   └── выгрузка расширения
    │
    └── ExtensionN/
        └── выгрузка расширения
```

`src/cf` необходимо воспринимать как основную конфигурацию.

Каждый непосредственный дочерний каталог внутри:

```text
src/cfe/
```

содержащий корректную выгрузку расширения 1С, необходимо автоматически обнаруживать как отдельное расширение.

Например:

```text
src/cfe/rs_main
src/cfe/edo_custom
src/cfe/client_changes
```

должны распознаваться как три независимых расширения одной основной конфигурации.

---

# 2. Один проект и один общий граф

Основную конфигурацию и все найденные расширения необходимо анализировать **в рамках одного запуска**.

Например:

```bash
graphify analyze ./src
```

должен автоматически обнаружить:

```text
./src/cf
./src/cfe/*
```

и построить единый граф проекта:

```text
1C Project
│
├── Base Configuration
│
├── Extension rs_main
│
├── Extension edo_custom
│
└── Extension client_changes
```

Не требуется запускать анализ каждого расширения отдельно.

Итоговый граф должен содержать одновременно:

```text
основную конфигурацию
+
все расширения
+
связи основной конфигурации
+
связи расширений
+
связи между конфигурацией и расширениями
+
по возможности связи между расширениями
```

---

# 3. Расширения нельзя физически сливать с основной конфигурацией

Несмотря на единый граф, происхождение каждого объекта необходимо сохранять.

Узел должен содержать информацию примерно следующего вида:

```text
source_type = configuration | extension
extension_name = null | <имя расширения>
source_path = ...
```

Например:

```text
source_type = configuration
extension_name = null
```

или:

```text
source_type = extension
extension_name = rs_main
```

Это необходимо для:

* анализа;
* фильтрации;
* визуализации;
* диагностики конфликтов;
* определения источника изменения.

---

# 4. Заимствованные объекты расширений

Если расширение заимствует объект основной конфигурации, нельзя считать его полностью независимым объектом.

Например существуют:

```text
Base:
Document.РеализацияТоваровУслуг

Extension rs_main:
Document.РеализацияТоваровУслуг
```

Создать отдельные узлы, но связать их:

```text
Extension.Document.РеализацияТоваровУслуг
        │
        │ EXTENDS
        ↓
Base.Document.РеализацияТоваровУслуг
```

Такой подход позволяет сохранить происхождение изменений и одновременно понимать, какой объект основной конфигурации расширяется.

---

# 5. Собственные объекты расширений

Объекты, созданные непосредственно в расширении и отсутствующие в основной конфигурации, являются полноценными объектами графа.

Например:

```text
Extension rs_main
    └── Catalog.рс_ВнешниеИдентификаторы
```

Если код обращается к этому объекту:

```bsl
Справочники.рс_ВнешниеИдентификаторы.НайтиПоКоду(...)
```

создать обычную ссылку:

```text
Procedure
    │
    │ REFERENCES
    ↓
Extension.rs_main.Catalog.рс_ВнешниеИдентификаторы
```

---

# 6. Методы расширений

Обязательно разрешать методы расширений относительно соответствующих методов основной конфигурации.

Например:

```bsl
&Перед("ОбработкаПроведения")
Процедура рс_ПередПроведением(...)
```

должно дать:

```text
ExtensionFunction
    │
    │ BEFORE
    ↓
BaseFunction
```

Для:

```bsl
&После(...)
```

создать:

```text
AFTER
```

Для:

```bsl
&Вместо(...)
```

создать:

```text
INSTEAD
```

Для:

```bsl
&ИзменениеИКонтроль(...)
```

создать:

```text
CHANGE_CONTROL
```

Не считать такие методы просто независимыми функциями BSL.

---

# 7. Несколько расширений одного метода

Особенно важно корректно поддерживать ситуацию, когда несколько расширений изменяют одну процедуру основной конфигурации.

Например:

```text
Extension A
    &Перед

Extension B
    &После

Extension C
    &ИзменениеИКонтроль
```

для:

```text
Document.РеализацияТоваровУслуг.ObjectModule.ОбработкаПроведения
```

В графе должны одновременно присутствовать все связи:

```text
ExtensionA.Method
       │
       │ BEFORE
       ↓
Base.Method
       ↑
       │ AFTER
       │
ExtensionB.Method

Base.Method
       ↑
       │ CHANGE_CONTROL
       │
ExtensionC.Method
```

Нельзя терять одну связь из-за того, что ранее была найдена другая.

---

# 8. Resolver должен учитывать весь effective project

Индексы символов необходимо строить с учетом:

```text
Base Configuration
+
Extension1
+
Extension2
+
...
+
ExtensionN
```

Resolver должен по возможности понимать:

* вызов Base → Base;
* вызов Extension → Base;
* вызов Extension → собственный объект Extension;
* вызов ExtensionA → объект или общий модуль ExtensionB;
* вызовы общих модулей;
* экспортные методы;
* глобальные модули;
* методы заимствованных объектов.

Если статически нельзя однозначно определить цель, создавать `AMBIGUOUS`, а не выбирать первый найденный вариант.

---

# 9. Effective Configuration

Помимо физического графа:

```text
Base + Extensions
```

предусмотреть архитектурную возможность строить представление:

```text
Effective Configuration
```

то есть логическое состояние конфигурации с учетом всех подключенных расширений.

Это не должно уничтожать исходные узлы.

Это дополнительное представление или вычисляемый слой.

Например пользователь должен в перспективе иметь возможность запросить:

```text
Покажи итоговую цепочку выполнения
Document.РеализацияТоваровУслуг.ObjectModule.ОбработкаПроведения
с учетом всех расширений
```

и получить последовательность примерно:

```text
ExtensionA BEFORE
        ↓
Base method
        ↓
ExtensionB AFTER
```

При наличии `INSTEAD`, `CHANGE_CONTROL` и нескольких расширений учитывать реальные известные правила платформы 1С настолько, насколько их возможно корректно восстановить статически.

Если порядок нескольких расширений нельзя достоверно определить из имеющихся данных, не придумывать его.

---

# 10. Визуализация является обязательной частью проекта

Graphify-1C должен сохранять и использовать существующую возможность Graphify визуально отображать граф.

Недостаточно только построить внутренний NetworkX / JSON / GraphML.

Пользователь должен иметь возможность открыть интерактивный граф в браузере.

Если текущий Graphify генерирует:

```text
graphify-out/graph.html
```

или аналогичный HTML-viewer, сохранить эту возможность.

1С-узлы и связи должны корректно отображаться в этом viewer.

# 15. Локальный граф выбранного объекта

Для крупных конфигураций нельзя пытаться постоянно показывать все десятки тысяч узлов.

Viewer должен поддерживать режим локального графа.

Например пользователь выбирает:

```text
ОбработкаПроведения()
```

и задает:

```text
Показать зависимости на 1 уровень
Показать зависимости на 2 уровня
Показать зависимости на 3 уровня
```

Результат:

```text
ОбработкаПроведения()
       ↓
ПродажиСервер.СформироватьДвижения()
       ↓
РегистрНакопления.Продажи
```

Также должны быть направления:

```text
Outgoing
Incoming
Both
```

то есть:

```text
Что вызывает эта процедура?
```

и:

```text
Кто вызывает эту процедуру?
```

Нужно уметь выбрать:

```text

```


# 17. Режим отображения расширений объекта

Для выбранного объекта добавить или предусмотреть режим:

```text
Показать изменения расширений
```

Например:

```text
                    rs_main
                       │
                     BEFORE
                       ↓

edo_custom ─ AFTER → Base.ОбработкаПроведения
                       ↑
                       │ CHANGE_CONTROL
                       │
                  client_fix
```

Пользователь должен быстро видеть:

* какие расширения изменяют объект;
* какие процедуры они изменяют;
* каким способом;
* какие новые методы добавляют;
* какие собственные объекты расширений участвуют в цепочке.

Viewer должен позволять искать как минимум по:

```text

имени процедуры
полному имени процедуры
имени расширения
```

Например:

```text
РеализацияТоваровУслуг
```

```text

```


После поиска должна быть возможность сфокусировать граф на найденном узле.

# 20. Навигация в исходный код

Если это позволяет текущая архитектура Graphify, сохранить ссылку на:

```text
file
start_line
end_line
```

чтобы в перспективе можно было перейти от узла графа непосредственно к исходному `.bsl`.

Даже если прямой переход через IDE пока не реализован, данные для этого должны сохраняться.

---

# 21. Масштабирование на ERP / КА / УТ

Учесть, что полноценные конфигурации могут давать:

```text
десятки тысяч metadata objects
десятки тысяч modules
десятки или сотни тысяч procedures/functions
сотни тысяч edges
```

Поэтому визуализация всей конфигурации одним неагрегированным графом не должна быть основным способом работы.

Использовать:

```text
aggregation
filtering
local subgraph
lazy rendering
communities
```

или существующие механизмы Graphify.

Необходимо избегать ситуации, когда открытие `graph.html` пытается одновременно отрисовать 100 000 узлов.

# 23. Не писать viewer с нуля без необходимости

Сначала изучить существующий HTML viewer Graphify.

Если существующая визуализация уже поддерживает:

```text
search
filtering
focus
communities
interactive nodes
```

расширить ее минимально необходимыми функциями.

Не создавать отдельное frontend-приложение, пока не доказано, что текущий viewer принципиально не подходит.

Основная цель остается:

> сохранить upstream-совместимость Graphify.

# 26. Definition of Done этого этапа

Поддержка `cf + cfe` считается реализованной, когда:

* `src/cf` автоматически определяется как основная конфигурация;
* все корректные проекты внутри `src/cfe/*` автоматически обнаруживаются;
* все они анализируются одним запуском;
* строится один общий граф;
* узлы сохраняют источник `configuration/extension`;
* сохраняется имя конкретного расширения;
* заимствованные объекты связываются с основной конфигурацией;
* собственные объекты расширений присутствуют в графе;
* `BEFORE` работает;
* `AFTER` работает;
* `INSTEAD` работает;
* `CHANGE_CONTROL` работает;
* несколько расширений одного метода не конфликтуют друг с другом в модели данных;
* viewer позволяет отличать Base от Extensions;
* viewer позволяет скрывать отдельные расширения;
* viewer позволяет искать объект/процедуру;
* viewer позволяет показать локальный подграф;
* viewer позволяет фильтровать типы связей;
* анализ большой конфигурации не требует отображения всего графа одновременно.

Ключевой принцип:

**Graphify-1C должен показывать не отдельные независимые графы основной конфигурации и расширений, а единый граф реального проекта 1С с сохранением происхождения каждого объекта и каждой модификации.**
